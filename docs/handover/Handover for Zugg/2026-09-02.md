## 2. Root cause of the dead pipeline (fixed)

The fleet was provisioned to send CSI to `192.168.195.229` (SER8). The sensing
server now runs on **cub13-linux at `192.168.195.233`**. `.229` is a *different,
live* machine on the LAN, so every frame went to the wrong host. The server
looked perfectly healthy the whole time — `status: ok`, zero errors, `tick: 0`.

**Failure signature to remember:** healthy server + `tick: 0` + `nodes: []`
means nobody is sending to *you*. Check the node's NVS `target_ip`, not the server.

Node 6 was re-provisioned on 2026-09-02 and is streaming. Nodes at `.182` and
`.224` are UP on the LAN but still not reporting — almost certainly still on `.229`.

## 3. TODO — in priority order

### 3.1 DHCP reservation for the server host  ← DO THIS FIRST
`192.168.195.233` is still a **dynamic lease**, and it is now baked into node 6's
NVS. When the lease moves, the whole pipeline dies again, silently, in exactly
the way described above.

- Reserve `192.168.195.233` for MAC `78:55:36:03:31:dd` (enp1s0, cub13-linux)
  on the gateway at `192.168.195.1` (HTTPS admin UI).
- Host-side alternative if the router is not accessible — pins the same address
  without touching the gateway:
  ```bash
  nmcli con mod "Wired connection 1" ipv4.method manual \
    ipv4.addresses 192.168.195.233/24 ipv4.gateway 192.168.195.1 ipv4.dns 192.168.195.1
  nmcli con up "Wired connection 1"
  # rollback:
  nmcli con mod "Wired connection 1" ipv4.method auto \
    ipv4.addresses '' ipv4.gateway '' ipv4.dns '' && nmcli con up "Wired connection 1"
  ```
  Caveat: a static address inside the DHCP pool can collide later. A router
  reservation is the cleaner fix.

### 3.2 Re-provision nodes `.182` and `.224`  (USB, ~1 min each)
They are alive but invisible to the server. This is an **NVS config write, not a
reflash**. One at a time, on `/dev/ttyUSB0`:

```bash
# 1. read the boot log first — gets the REAL node_id and settles 3.3
python3 -m serial.tools.miniterm /dev/ttyUSB0 115200   # Ctrl-] to exit

# 2. then provision, with the node_id you just read
python3 firmware/esp32-csi-node/provision.py \
  --port /dev/ttyUSB0 --target-ip <server-ip> --node-id <n> --edge-tier 2
```

**ALWAYS pass `--node-id` explicitly.** `provision.py` merges prior state keyed
by *serial port*, and boards move between ports. The state file for
`/dev/ttyUSB0` said `node_id: 1` while the board on it was node 6 — a bare
re-provision would have relabelled node 6 as node 1. Same trap `c9f81bfe`
documented.

**Also always pass `--edge-tier 2`.** `build_nvs_csv` only writes the keys it is
given and flashing replaces the whole partition, so any key absent from the
merged state is silently lost. The state file has no `edge_tier`, but the boards
run `edge_tier=2`.

`--dry-run` writes `nvs_config.csv` + `nvs_provision.bin` into CWD **containing
the WiFi password in plaintext**. Both are gitignored (`**/nvs_*.csv`,
`**/nvs_*.bin`) but delete them after every run.

**The one to check on hardware.** Upstream's ADR-297 (issue #1554) replaced the
local `classify_vitals` + node-count confidence boost with
`classification_from_room(&room_inference)`. But upstream's version is a *pure

against a known-empty room. Site is marked `REBASE NOTE (2026-09-01)` in
`v2/crates/wifi-densepose-sensing-server/src/main.rs`.

Related smell seen live: node 6 reporting `motion_level: present_still` with
`person_count: 2`, and the boot log showed `persons=4` from edge vitals.

## 5. Things that bit us — worth not re-learning

- **`/tmp` worktree ate work.** `zugg/upstream-presence-vitals-triage` lived in
  `/tmp/ruview-upstream-fix-triage`; `/tmp` was cleared. Commits survived in the
  shared `.git`, uncommitted changes would not have. Don't put worktrees in `/tmp`.
- **Three weeks of work sat uncommitted** in the worktree (firmware active-TX
  experiment, desk-occupancy server changes, camera-oracle changes, July
  calibration captures). Now committed.
- **`.cargo-target-bookworm/`** — 837M untracked cargo target dir, would have
  been swept into a bulk `git add`. Now gitignored.
- **Six submodules have stale working-tree checkouts** though all six *pointers*
  match `origin/main`. `vendor/rufield` had to be synced before the workspace
  would build (`git submodule update --init vendor/rufield`). If you hit
  `E0560 ... has no field named ...` in `wifi-densepose-rufield`, that's this.
- **`libudev-dev`** is required for the full workspace build (`ruview-twin`,
  `homecore-automation`). Installed 2026-09-02.
- **OTA cannot rescue a mis-provisioned node.** `max_size` is 921600 vs a
  ~1.14MB image, so the first upgrade per node must be USB regardless.
